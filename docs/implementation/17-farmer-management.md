# 17 — Farmer Management

## Goal

Implement farmer management in the desktop application through the authenticated stall-service API.

Authorized staff can register a farmer, find them by short code or name, edit their details, and deactivate or reactivate their record.

Farmer records belong to the stall’s authoritative SQLite database. Successful changes must include audit and outbox records so later synchronization can carry them to the cloud.

Keep production authorization fail-closed while the previously recorded offline-policy decisions remain unresolved. Use explicitly labeled test policies for automated verification.

## 2. Define the Farmer Record

Use fields supported by the existing schema and approved requirements.

The initial form should cover:

| Field | Behavior |
| --- | --- |
| Internal ID | Stable, generated by the service using the established ID strategy. |
| Farmer short code | Required and unique within the approved stall/code scope. |
| Display name | Required, with Sinhala and English support. |
| Contact number | Optional unless the approved context requires it. |
| Address or locality | Optional where supported by the schema. |
| Active status | Determines availability for new operational selections. |
| Revision | Supports concurrent-edit detection. |
| Created/updated metadata | Assigned by the service. |

Keep financial balances and opening-balance entry in their assigned accounting phases.

Farmer registration creates a business record. Authentication remains attached to staff accounts.

### Short-Code Rules

Follow the approved code format, normalization, and uniqueness scope.

If these are missing, record a proposed rule before creating constraints that depend on it. Continue independent work while the decision is unresolved.

Requirements:

- Preserve the distinction between the internal ID and short code.
- Enforce uniqueness in SQLite as well as application validation.
- Keep deactivated records within the uniqueness scope to prevent accidental code reuse.
- Treat duplicate names as valid.
- Treat phone numbers as text and preserve leading zeros.
- Apply documented normalization consistently during creation, lookup, and editing.

Keep the short code read-only after creation unless an approved correction policy exists. If code changes are supported, preserve the internal identity and audit the previous code.

- Creating a farmer.
- Updating approved editable fields.
- Changing farmer status.
- Reading one farmer.
- Searching and listing farmers.
- Returning paginated results.

Include expected revisions for updates and status changes.

Use the existing idempotency convention for mutations.

Validate:

- Empty or whitespace-only names and codes.
- Optional-field clearing.
- Pagination limits.
- Search parameters.
- Allowed status values.

Define the difference between an omitted field and an explicit request to clear an optional field.

Return only the fields needed by the caller.

## 4. Implement Farmer Repositories and Commands

Add tenant-scoped repository operations for:

- Create.
- Read by ID.
- Exact short-code lookup.
- Paginated search.
- Update with an expected revision.
- Activate or deactivate with an expected revision.

Use parameterized queries and explicit row mapping.

Every command must derive the tenant, staff actor, and device from the verified execution context.

Execute each successful mutation through the phase 10 transaction boundary so these commit together:

- Farmer record changes.
- Revision advancement.
- Audit event.
- Outbox event.
- Idempotency result.

A failed write must roll back all associated effects.

### Concurrent Requests

- Competing creates with the same normalized code must produce one farmer and one clear conflict.
- Retrying a successful create with the same idempotency key must return its original result.
- Reusing a key with different input must return a conflict.
- A stale update must preserve the newer stored version.
- Repeated submission must not create duplicate audit or outbox effects.

## 5. Expose Authenticated Farmer Endpoints

Follow the service’s existing API prefix and naming conventions.

Provide operations equivalent to:

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/farmers` | Search and list permitted farmer records. |
| GET | `/farmers/:id` | Read one farmer. |
| POST | `/farmers` | Register a farmer. |
| PATCH | `/farmers/:id` | Update approved details. |
| PATCH | `/farmers/:id/status` | Activate or deactivate a farmer. |

Reuse existing capability identifiers for viewing and managing farmer records. Add a capability only if the existing catalog cannot express a required action, and document its owner-assignment behavior.

Verify device identity, staff session, effective capabilities, and tenant ownership on every operation.

Return safe shared errors for validation failures, duplicate codes, missing records, stale revisions, and denied access.

Keep administrative deletion outside the farmer interface. Deactivation preserves historical references.

## 6. Implement Search for Fast Operational Use

Support:

- Exact short-code lookup.
- Code-prefix search.
- Display-name search.
- Active/inactive filtering.
- Bounded pagination.

Prioritize exact code matches and use a stable tie-breaker for the remaining results.

Document actual case and Unicode behavior. Verify Sinhala search using representative names.

Escape search metacharacters when the user input is intended as literal text.

Use indexes supported by the existing schema. Add a forward migration only when a necessary field, constraint, or index is missing.

For desktop search:

- Debounce typing modestly.
- Cancel or ignore stale requests.
- Show loading and empty states.
- Preserve keyboard focus.
- Clear results when the staff or stall context changes.

Operational lookup should default to active farmers. Management screens must allow staff with permission to find inactive records.

## 7. Build the Desktop Farmer Screen

Enable the Farmers navigation entry.

Use the shared design system and existing service connection.

Provide:

- Search field.
- Active-status filter.
- Farmer table.
- Add Farmer action.
- Details/edit view.
- Deactivate/reactivate actions.

Show short code, name, relevant contact information, and status.

Use a page or accessible side panel for editing, with visible Save and Cancel actions. Keep the flow efficient for keyboard users.

### Create

1. Open the form and focus the first field.
2. Enter the short code, name, and optional details.
3. Validate inline.
4. Submit once using a stable idempotency key.
5. Show success only after the host confirms the transaction.
6. Refresh the relevant list and focus the created record.

Keep entered values available after a recoverable error.

### Edit

Load the current record and revision.

On a revision conflict, preserve the staff member’s unsaved input and explain that another terminal updated the record. Offer reload and deliberate reconciliation.

Do not silently overwrite the newer version.

### Connection and Session Changes

When the host is unavailable, disable service-dependent actions and show the phase 16 connection state.

When a staff session ends or the staff member changes, clear private record data and unsaved form state according to the established logout behavior.

For a timed-out save, retain the original operation identity and use the existing idempotent retry behavior. Show an uncertain outcome until the result is resolved.

## 8. Implement Safe Deactivation

Deactivation must:

- Preserve the farmer ID and code.
- Preserve references from existing bills and other historical records.
- Remove the farmer from default new-transaction selection.
- Remain visible in management searches when inactive records are included.
- Record the actor, timestamp, and revision.

Reactivation restores eligibility for new selections using the same identity.

If parties can serve as both farmers and buyers, apply the approved role-specific status behavior. Avoid disabling the buyer role as an accidental consequence of farmer deactivation.

Document the service-side active-record check that billing commands will enforce later. The lookup filter alone cannot enforce transaction eligibility.

## 11. Perform a Two-Terminal Acceptance Check

Use a synthetic farmer such as `Test Farmer A` and a code valid under the implemented rules.

1. On Terminal A, sign in with farmer-management permission and create the record.
2. On Terminal B, search for that code and verify the host returns the same record.
3. Open the farmer for editing on both terminals.
4. Save a change on Terminal A.
5. Attempt to save the older revision on Terminal B and verify a conflict.
6. Deactivate the farmer and verify default operational lookup excludes it after refresh.
7. Reactivate it and verify the original ID and code remain.
8. Disconnect internet access while preserving the LAN and repeat an authorized lookup or edit within the approved offline policy.
9. Stop the host and verify both terminals block host-dependent operations.

If production offline policy remains unresolved, report that acceptance step as blocked. Keep the documented production fail-closed behavior.
