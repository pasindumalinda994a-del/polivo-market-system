# 18 — Buyer and Trader Management

## Goal

Implement buyer/trader management in the desktop application through the authenticated stall-service API.

Authorized staff can register a trader, search by short code or name, edit details, and deactivate or reactivate the record.

Reuse phase 17’s farmer-management foundations while preserving the distinction between farmer and buyer roles.

## 1. Inspect the Existing Implementation

1. Read `AGENTS.md`, the six context files, and accepted business decisions.
2. Read `docs/context/progress-tracker.md`.
3. Inspect phase 17’s actual schema, repositories, contracts, routes, IPC methods, UI, and tests.
4. Review the existing party-role model and short-code uniqueness rules.
5. Inspect the effective-capability checks and authenticated desktop service client.
6. Mark phase 18 as in progress.

Reuse working validation, search, transaction, and UI patterns where their behavior fits buyer management.

Check the actual farmer migration before adding another migration. Preserve existing farmer records, identifiers, and migration checksums.

Continue to enforce the recorded production fail-closed policy while offline authorization decisions remain unresolved. Use explicitly labeled test policies for automated verification.

## 2. Establish Consistent Terminology

Use the existing project convention for “buyer” and “trader.”

For this module, both refer to the party purchasing vegetables from the stall.

If the implementation uses `buyer` internally, keep that naming consistent across contracts, repositories, and routes. Use the approved customer-facing label in the desktop interface.

Registration creates a stall business record. Web membership and local staff access follow their existing account-management workflows.

## 3. Define the Buyer Record

Use fields supported by the current schema and approved requirements.

| Field | Behavior |
| --- | --- |
| Internal ID | Stable identity generated by the service. |
| Short code | Required and unique within the established scope. |
| Display name | Required, supporting Sinhala and English. |
| Contact number | Optional unless existing requirements make it mandatory. |
| Address or locality | Optional where supported by the schema. |
| Active status | Controls eligibility for new buyer selections. |
| Revision | Supports concurrent-edit detection. |
| Created/updated metadata | Assigned by the service. |

Keep contact numbers as text and preserve leading zeros.

Follow phase 17’s rules for whitespace, lengths, optional-field clearing, code normalization, and Unicode handling where applicable.

Duplicate display names are valid. Name or phone similarity alone must never trigger automatic record merging.

Short codes and internal IDs remain separate from the trader bill-number sequence.

Financial balances, credit limits, opening balances, and settlements belong to their assigned phases.

## 4. Preserve Shared Party Behavior

Inspect whether the current model represents:

- Separate farmer and buyer records.
- A shared party with one role.
- A shared party with multiple roles.

Implement buyer management using that established model.

### If Multiple Roles Are Supported

- Require explicit selection of an existing party before adding its buyer role.
- Preserve its farmer role and historical references.
- Detect duplicate role assignment.
- Apply the approved role-specific activation behavior.
- Explain when editing shared contact details affects both views.

### If Roles Are Separate

Preserve the separate identities and existing uniqueness constraints.

Record any future dual-role requirement as a separate decision rather than redesigning the party model during this phase.

Use the existing code-uniqueness scope. If codes are globally unique per stall, a farmer code may also conflict with a new buyer code. Present the actual rule clearly.

Include expected revisions for updates and status changes.

Reuse common party schemas where they preserve the established farmer behavior. Keep buyer-specific contracts explicit.

## 6. Implement Buyer Repositories and Commands

Add tenant-scoped operations for:

- Create.
- Read by ID.
- Exact short-code lookup.
- Paginated search.
- Update with an expected revision.
- Activate or deactivate with an expected revision.

Every buyer query must enforce the relevant buyer role or record type.

A farmer-only record must not become editable through a buyer endpoint simply because its ID exists in the same table.

Use parameterized queries and the existing database mapping conventions.

### Transaction Requirements

Each successful mutation must atomically persist:

- The party or buyer changes.
- Revision advancement.
- Audit records.
- Outbox events.
- The idempotency result.

Reuse phase 10’s transaction executor.

A failure in any required write must roll back the entire operation.

### Concurrency and Retries

- Concurrent requests for the same normalized code must produce one successful registration.
- Repeating a successful command with its original key must return the recorded result.
- Reusing a key with different input must return a conflict.
- Stale revisions must preserve the newer stored version.
- Idempotency scope must distinguish buyer commands from farmer commands.

Use forward migrations only for necessary missing fields, constraints, or indexes.

## 7. Expose Authenticated Buyer Endpoints

Follow the service’s current API prefix and route conventions.

Provide operations equivalent to:

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/buyers` | Search and list buyers. |
| GET | `/buyers/:id` | Read one buyer. |
| POST | `/buyers` | Register a buyer. |
| PATCH | `/buyers/:id` | Update approved details. |
| PATCH | `/buyers/:id/status` | Activate or deactivate a buyer. |

Reuse the capability assignment established by phase 17.

If `parties.register_edit` currently controls party management, preserve that behavior. A cashier gains management access only when the owner’s effective assignment permits it.

Future billing lookup may require a narrower capability. Document that extension for the billing phase.

Verify device identity, staff session, current capabilities, tenant ownership, and buyer role on every operation.

Map validation, duplicate-code, missing-record, stale-revision, and access errors through the shared public error format.

## 8. Implement Search and Lookup

Support:

- Exact short-code lookup.
- Code-prefix search.
- Display-name search.
- Active/inactive filtering.
- Bounded pagination.

Reuse phase 17’s normalization and stable ordering.

Prioritize exact code matches and use a deterministic tie-breaker.

Verify Sinhala search and literal handling of search metacharacters.

Operational lookup should default to active buyers. Management screens must support finding inactive records.

Keep results scoped to the bound stall and buyer role.

Do not load the entire parties table into the renderer for filtering.

## 11. Handle Deactivation and Connection Failures

Deactivation must preserve:

- Internal identity.
- Short code.
- Existing bill and payment references.
- Historical audit records.

It removes the buyer from default new-transaction selection while keeping the record available through management filters.

Reactivation restores eligibility using the same identity.

When a party has both roles, follow the established role-specific status policy.

Future billing commands must validate current buyer eligibility at the service write boundary.

### Connection Failures

- Disable host-dependent actions when the host is unavailable.
- Keep recoverable form input while the same authorized staff context remains active.
- Resolve an uncertain save using its original operation identity.
- Clear private list and form state when the staff session ends.
- Show `Saved locally` only after a confirmed local commit.

Keep cloud-sync status tied to actual synchronization evidence.

## 12. Add Audit and Outbox Events

Follow phase 17’s event conventions.

Define concrete validated events for:

- Buyer creation.
- Buyer detail updates.
- Buyer status changes.
- Explicit buyer-role assignment, if supported.

Include the source record ID, tenant, revision, event version, timestamp, and permitted actor/device metadata.

Keep payload semantics consistent with the shared-party model.

If farmer and buyer views share contact fields, emit the canonical party change needed to keep both views consistent during later synchronization.

Avoid duplicate logical events that would independently overwrite the same shared record.

Persist events in the same transaction as the record change.
